## ADR-008 — Stratégie de tests

**Contexte :** Le projet est développé par un développeur solo disposant du
matériel (montre FR55) et d'un accès au compte Garmin Connect. Les ADR-002 à
ADR-007 définissent une architecture modulaire testable unitairement, mais
aucune stratégie de test n'est formalisée. L'exigence implicite est la
suivante : **chaque session de développement se termine par des tests qui
passent**, et **chaque jalon d'epic est validé par des tests d'intégration
réelle** (montre branchée, GC disponible).

**Décision :** Trois niveaux de tests via **pytest**, marqués avec des markers
dédiés, avec skip automatique quand les dépendances réelles sont absentes.

---

### Trois niveaux de tests

| Niveau | Marker | Déclenchement | Environnement | Objectif |
|--------|--------|--------------|---------------|----------|
| **Unitaire** | `unit` | **Chaque fin de session de dev** | Mocks uniquement | Valider la logique interne de chaque module isolément |
| **Intégration réelle** | `integration` | **Jalons d'epic** + quand la montre est branchée | Montre FR55 réelle montée en USB | Valider la chaîne USB : détection, lecture/écriture FIT, copie |
| **Réseau réel** | `network` | **Jalons d'epic** + quand GC est disponible | Compte Garmin Connect réel | Valider auth, appels API, upload/download, rate limiting |

### Règles d'exécution

```
# Fin de chaque session de dev — doit passer
pytest -m unit

# Jalons d'epic — avec montre branchée et GC disponible
pytest -m "integration or network"

# Tout (quand tout est dispo)
pytest
```

Le `conftest.py` applique un `skip` automatique via `pytest.skip()` si :
- **`integration`** : la montre n'est pas montée (`/run/media/$USER/GARMIN/GARMIN/GarminDevice.xml` absent)
- **`network`** : les credentials sont absents du keyring GNOME

Ces skips évitent les faux échecs quand le matériel n'est pas connecté.

### Stratégie de mock par couche

| Module testé | Dépendance mockée | Comment |
|-------------|-------------------|---------|
| `fit/decoder` | Aucune (entrée : `bytes`) | Test purement fonctionnel sur fixtures FIT |
| `store/` | Aucune (SQLite en `:memory:`) | Base temporaire créée/détruite par test |
| `watch/detector` | `pyudev`, `os.path.exists` | Injection d'événements simulés |
| `watch/filesystem` | Montre réelle → `fixtures/watch_tree_mock/` | `tmp_path` pytest avec arborescence copiée |
| `garmin/client` | `garminconnect.Garmin` | Mock de l'objet `Garmin()` — les tests unitaires ne font jamais de HTTP |
| `sync/*` | `GarminClient` + `WatchFilesystem` mockés | Les services sont testés avec des faux clients |
| `auth/authenticator` | `garminconnect.Garmin`, `secretstorage` | Mock du login et du keyring |
| `ui/` | Tous les services mockés | Tests UI hors périmètre de cet ADR (responsabilité UX Designer) |

---

### Couverture cible

| Epic | Modules | Couverture unitaire cible |
|------|---------|--------------------------|
| 1 — Auth | `auth/`, `garmin/` | > 80% |
| 2 — Cloud → Montre | `sync/workouts`, `watch/`, `fit/` | > 80% |
| 3 — Montre → Cloud | `sync/activities`, `sync/wellness`, `fit/` | > 80% |
| 4 — UI | `ui/`, `sync/history` | > 60% (logique UI difficile à tester unitairement) |

La couverture est mesurée avec `pytest --cov=src/openrunner55 --cov-report=term`.
Le seuil est indicatif — le critère réel de succès est que les tests unitaires
et d'intégration réelle passent aux jalons définis.

---

### Jalons de test par epic

| Jalon | Quand | Tests requis |
|-------|-------|-------------|
| **E1** | Fin Epic 1 (Auth) | `unit` : auth, garmin, store. `network` : auth réelle, tokenstore. |
| **E2** | Fin Epic 2 (Cloud → Montre) | `unit` : sync/workouts, watch, fit. `integration` : montre réelle. `network` : download réel. |
| **E3** | Fin Epic 3 (Montre → Cloud) | `unit` : sync/activities, sync/wellness, fit. `integration` : lecture montre. `network` : upload réel. |
| **E4** | Fin Epic 4 (UI) | `unit` : sync/history, store. `network` + `integration` : chaîne complète (régression E1-E3). |

À chaque jalon, **tous les tests des jalons précédents doivent continuer à
passer** (régression). Exemple : au jalon E3, on repasse la batterie E1 + E2.

---

### Dépendances

- **`pytest`** — framework standard Python, via pip
- **`pytest-cov`** — mesure de couverture (optionnel, via pip)
- **`garminconnect`** — déjà dans les dépendances du projet (pour les mocks et les tests network)

Aucune dépendance système supplémentaire pour les tests unitaires. Les tests
`integration` nécessitent la montre FR55 branchée. Les tests `network`
nécessitent des credentials dans le keyring GNOME et une connexion Internet.

---

### Alternatives écartées

| Alternative | Raison du rejet |
|------------|-----------------|
| **`unittest` (stdlib)** | Moins expressif que pytest, fixtures plus verbeuses, paramétrage limité |
| **Tests uniquement manuels** | Pas reproductible, pas de régression automatisée, ne correspond pas à la discipline « chaque session se termine par des tests » |
| **Mock de la montre en boucle (pas de tests réels)** | Risque de bugs silencieux : un mock peut cacher une incompatibilité réelle (encodage FAT32, latence USB, fichiers verrouillés) |
| **CI/CD** | Overkill pour un projet solo sans serveur. Les tests sont lancés localement. |
| **TDD strict** | Non imposé. Les tests sont écrits avant ou après le code, au choix du développeur, tant qu'ils passent en fin de session. |

---

### Conséquences

- **Discipline :** `pytest -m unit` est le dernier geste avant `git commit`.
  Une session de dev n'est pas terminée tant que ce n'est pas vert.
- **Jalons :** chaque fin d'epic déclenche une session dédiée avec la montre
  branchée et GC accessible pour valider l'intégration réelle.
- **`conftest.py` partagé :** un seul fichier de configuration pour tous les
  tests, avec les markers et les conditions de skip. Pas de duplication.
- **Fixtures réelles :** les échantillons FIT du spike S-2 sont conservés dans
  `tests/fixtures/fit_samples/` et servent de référence pour les tests
  unitaires du `FitDecoder`.
- **Le développeur juge :** si une session de dev est purement exploratoire
  (spike, prototypage), la règle des tests unitaires peut être assouplie.
  Mais tout code destiné à rester dans le dépôt est testé.

**Références :** ADR-002 pour l'architecture modulaire, ADR-005 pour la
persistance SQLite, ADR-006 pour la détection USB, ADR-007 pour le rate
limiting. Spike S-2 pour les échantillons FIT et les scripts de référence.
