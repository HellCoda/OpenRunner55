## ADR-007 — Rate limiting et robustesse réseau

**Contexte :** Le spike S-2 a confirmé la présence de rate limiting HTTP 429
sur les endpoints Garmin Connect (par IP, pas par compte). Les routes
`mobile` sont systématiquement bloquées (429 ou 403 Cloudflare). Le
`di_token` JWT a une durée de vie d'environ 1 jour et doit être rafraîchi.
Les échecs réseau (timeout, DNS, 5xx) et les erreurs API (401, 403, 406)
doivent être gérés sans perte de données ni blocage de l'application.
L'exigence EF-19 impose un backoff exponentiel sur les 429. L'exigence
EF-20 impose une gestion propre des interruptions.

**Décision :** Stratégie de retry centralisée dans le module `garmin/client.py`.
Tout appel à l'API Garmin Connect passe par ce wrapper.

### Délai inter-requêtes

Un délai minimum de **3 secondes** entre deux requêtes API consécutives
(depuis le même processus). Implémenté via un attribut `_last_request_time`
et `time.sleep()` si nécessaire. Ce délai est **préventif** : il vise à ne
pas déclencher le 429, par opposition au backoff exponentiel qui est
**réactif** (après un 429 reçu).

#### Impact sur ENF-1 (performance)

Pour 10 workouts, le parcours GC → Montre génère 11 requêtes API
(1 × `get_workouts` + 10 × `download_workout`), soit ~33s d'espacement
préventif à 3s/requête. Avec le téléchargement et la copie USB, le temps
total perçu par l'utilisateur sera de l'ordre de **40 à 60 secondes**.

→ **À ajuster après tests réels.** Les 3s sont un point de départ
conservateur. Si Garmin tolère des délais plus courts (ex: 1s) sans
déclencher de 429, le délai sera réduit. Si au contraire des 429
apparaissent, il sera augmenté. La valeur de 3s est une **constante
configurable** (`INTER_REQUEST_DELAY`) dans `garmin/client.py`.

### Backoff exponentiel sur 429

En cas d'erreur `GarminConnectTooManyRequestsError` :

| Tentative | Délai avant retry | Délai cumulé |
|-----------|-------------------|-------------|
| 1 (retry) | 1 s | 1 s |
| 2 (retry) | 2 s | 3 s |
| 3 (retry) | 4 s | 7 s |
| Échec     | Abandon           | 7 s (backoff seul) |

Maximum **3 retries**. Après épuisement, l'erreur est remontée à la couche
Service, qui la journalise et la transmet à l'UI pour affichage.

### Interruption USB (EF-20)

Si la montre est débranchée pendant un transfert (détection par `WatchDetector`,
cf ADR-006), l'opération en cours est interrompue :
- Les fichiers déjà écrits restent sur la montre (pas de rollback).
- Le fichier en cours d'écriture est signalé comme incomplet dans l'historique.
- L'utilisateur est notifié via l'UI.
- L'état de chaque fichier (réussi/échoué/incomplet) est persisté dans
  `sync_history.details` (JSON) pour permettre une reprise ciblée.

### Gestion du 401 (token expiré)

Le `di_token` expire après ~1 jour. Le refresh automatique de `garminconnect`
est proactif (15 min avant expiry) mais peut échouer (endpoint down, réseau).

1. L'appel API reçoit un 401.
2. `garmin/client.py` appelle `auth.authenticator.refresh_session()`.
3. Si le refresh échoue → `auth.authenticator.resume_session()` (re-login
   depuis le tokenstore).
4. Si le re-login échoue → `auth.authenticator.login(credentials)` (fresh
   login avec les credentials du keyring).
5. Si tout échoue → l'erreur est remontée à l'UI : « Session expirée,
   veuillez vérifier vos identifiants. »
6. Aucune opération de sync n'est lancée tant que l'auth n'est pas rétablie.

**Respect des couches :** `auth/` et `garmin/` sont tous deux dans la couche
Core (cf. ADR-002). L'appel de `garmin/client.py` vers `auth/` pour la
cascade 401 est un appel intra-couche — il ne viole pas la règle cardinale
UI → Services → Core.

### Gestion des autres erreurs

| Erreur | Stratégie | Retry ? |
|--------|-----------|---------|
| **429** Too Many Requests | Backoff exponentiel | ✅ 3 retries |
| **5xx** Server Error | Backoff exponentiel | ✅ 3 retries |
| **401** Unauthorized | Refresh → re-login | ✅ (cascade auth) |
| **403** Forbidden / Cloudflare | Pas de retry. L'endpoint est bloqué structurellement | ❌ |
| **406** Not Acceptable (ex: SUMMARY) | Pas de retry. Fichier non supporté. Journalisé, skip. | ❌ |
| **Timeout / DNS / réseau** | Backoff exponentiel | ✅ 3 retries |
| **InvalidFileFormat** | Pas de retry. Fichier corrompu. Journalisé, skip. | ❌ |

### Interface du module `garmin/client.py`

```python
class GarminClient:
    # Configuration
    INTER_REQUEST_DELAY = 3.0      # secondes
    MAX_RETRIES = 3
    RETRY_BASE_DELAY = 1.0         # secondes (×2 à chaque retry)

    def __init__(self, authenticator: Authenticator)
    def get_workouts(start=0, limit=20) -> list[dict]
    def download_workout(workout_id: int) -> bytes
    def upload_activity(file_path: str) -> dict
    def get_activities(start=0, limit=20) -> list[dict]
```

Chaque méthode publique applique : délai inter-requêtes → appel API → capture
des erreurs → retry si applicable → re-login si 401 → remontée d'exception
propre (`SyncError`) à la couche Service.

**Alternatives écartées :**

- **Retry illimité** — risque de boucle infinie, aggrave le rate limiting,
  bloque l'UI.
- **Pas de retry du tout** — l'utilisateur doit relancer manuellement à
  chaque 429 ou erreur réseau passagère. Expérience dégradée.
- **Backoff linéaire** (1s, 2s, 3s) — moins efficace que l'exponentiel
  contre le rate limiting. Garmin peut appliquer des pénalités croissantes.
- **Délai inter-requêtes dynamique** (ajusté selon les 429 reçus) — complexité
  inutile pour un usage manuel ponctuel (quelques dizaines de requêtes par
  session).
- **File d'attente de requêtes** — overkill. Pas de sync en arrière-plan,
  pas de parallélisme. Une requête à la fois, séquentielle.

**Conséquences :**

- **Centralisation dans `garmin/client.py`** : toute la logique réseau est
  isolée dans un module unique. Les services `sync/*` et l'UI ne gèrent
  jamais de HTTP, de retry, ou de rate limiting.
- **Timeout total max par requête :** ~25 secondes dans le pire cas
  (backoff cumulé : 7s + délais inter-requêtes : 3 × 3s = 9s + 4 appels
  HTTP à ~2s = ~8s réseau). Une requête qui réussit au 1ᵉʳ appel ne subit
  aucun surcoût. Acceptable pour une utilisation manuelle.
- **Paramètres configurables** via constantes de classe — permet d'ajuster
  sans modifier la logique si Garmin change son comportement.
- **Toutes les erreurs sont journalisées** dans `operation_logs` (ADR-005)
  pour diagnostic ultérieur.
- **L'UI n'est jamais bloquée :** les appels API longs (upload, download)
  sont exécutés dans un thread séparé via `GLib.Thread` ou `asyncio`, l'UI
  reste responsive et affiche une barre de progression.

et la co-localisation `auth/`/`garmin/` en Core. ADR-004 pour la cascade
