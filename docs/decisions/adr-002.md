## ADR-002 — Architecture modulaire en 3 couches

**Contexte :** L'exigence ENF-6 impose un code structuré en modules (auth, API
Garmin, USB/montre, UI, logs). Le spike S-2 a validé 5 blocs fonctionnels
indépendants (auth headless, persistance session, upload activité, upload
wellness, roundtrip workout). Les recommandations du spike proposent un
découpage en 7 modules. Le projet doit rester maintenable par un développeur
solo, testable unitairement, et permettre l'ajout futur d'un mode CLI sans
refactoring.

**Décision :** Architecture en 3 couches — **UI**, **Services**, **Core** —
avec 7 packages Python (10 modules de responsabilité métier).

```
┌────────────────────────────────────────────────┐
│  UI Layer         src/openrunner55/ui/         │  ← GTK 4 (cf ADR-003)
│  app, auth_view, watch_view, history_view,     │    Responsabilité UX Designer
│  account_view, widgets                         │    (cf ux-design.md)
└────────────────────┬───────────────────────────┘
                     │  Appelle uniquement les Services
┌────────────────────┴───────────────────────────┐
│  Service Layer     src/openrunner55/sync/      │  ← Orchestration métier
│  workouts, activities, wellness, history       │    Tests unitaires sans UI
└────────────────────┬───────────────────────────┘
                     │  Appelle le Core
┌────────────────────┴───────────────────────────┐
│  Core Layer                                    │
│  src/openrunner55/auth/              (auth)    │  ← Accès données
│  src/openrunner55/garmin/client.py   (API GC)  │    Pas de logique métier
│  src/openrunner55/watch/             (montre)  │    Auth et Garmin co-localisés
│  src/openrunner55/fit/decoder.py     (FIT)     │    car garminconnect fusionne
│  src/openrunner55/store/             (SQLite)  │    auth + client API
└────────────────────────────────────────────────┘
```

| Module | Couche | Responsabilité |
|--------|--------|---------------|
| `auth/` | Core | Login headless via `garminconnect`. Tokenstore (`~/.config/openrunner55/tokens.json`). Credentials dans GNOME Keyring (cf ADR-004). Refresh automatique. MFA non supporté (risque résiduel, cf ADR-004). Co-localisé avec `garmin/` dans la même couche car `garminconnect` fusionne auth et client API dans un même objet ; `garmin/client.py` appelle `auth/` pour le re-login 401 sans violation de couche. |
| `garmin/` | Core | Wrapper autour de `Garmin()` de `garminconnect`. Rate limiting (429 → backoff), 401 → re-login via `auth`. Timeout, retry. Interface unique pour tous les appels API GC. |
| `watch/` | Core | Détection USB via pyudev + polling fallback (cf ADR-006). Identification FR55 via `GarminDevice.xml`. Lecture/écriture des dossiers Activity, Workouts, Monitor, Sleep, Metrics. |
| `fit/` | Core | Décodage .FIT via `garmin-fit-sdk`. Extraction métadonnées (type, date, sport). Classification (activité vs wellness vs workout). Vérification intégrité. |
| `store/` | Core | SQLite (cf ADR-005). CRUD historique de syncs (`sync_history`), logs d'opération (`operation_logs`), état des fichiers transférés (`transferred_files` — déduplication locale). |
| `sync/workouts.py` | Service | Récupération liste workouts GC → téléchargement .FIT → slugify(nom) + gestion collisions → copie USB vers `Workouts/{slug}.FIT`. Déduplication via `store/transfers.py`. |
| `sync/activities.py` | Service | Lecture `Activity/` → classification → upload vers GC. Déduplication via `store/transfers.py` (table `transferred_files`) : un fichier déjà uploadé est ignoré. |
| `sync/wellness.py` | Service | Upload `Monitor/`, `Sleep/`, `Metrics/` → GC via endpoint générique. Exclusion `SUMMARY/`. |
| `sync/history.py` | Service | Consultation en lecture seule de l'historique et des logs. Seul point d'entrée UI pour `store/` — l'UI n'appelle jamais `store/` directement. `get_operation_logs(limit, level)` avec filtre optionnel par niveau (DEBUG/INFO/WARN/ERROR). |
| `ui/app.py` | UI | Application GTK, fenêtre principale, navigation latérale (montre, historique, compte). |
| `ui/auth_view.py` | UI | Écran de login pré-authentification (fenêtre centrée, pas de navigation). |
| `ui/watch_view.py` | UI | Vue montre unifiée (GC → Montre + Montre → GC) avec séparation visuelle des sources. |
| `ui/history_view.py` | UI | Vue historique des syncs + logs (appelle `sync/history.py`). |
| `ui/account_view.py` | UI | Section post-authentification « Compte & Paramètres » : email GC, statut connexion, stockage, version. Action : « Se déconnecter » → `auth.delete_credentials()` + suppression tokenstore → redirection `auth_view`. |
| `ui/widgets.py` | UI | Composants GTK réutilisables. |

**Règle cardinale :** La couche N appelle uniquement la couche N-1. L'UI
appelle les Services. Les Services appellent le Core. Jamais l'inverse. Pas
de dépendance circulaire.

**Note — Auth en Core :** Le module `auth/` est placé en Core plutôt qu'en
Service car la bibliothèque `garminconnect` fusionne l'authentification et le
client API dans un seul objet `Garmin()`. Placer `auth/` en Service aurait
créé une dépendance circulaire (Core → Service sur erreur 401). En les
co-localisant dans Core, `garmin/client.py` peut appeler `auth/` pour le
re-login transparent sans violer la règle cardinale. Cette décision reflète
la réalité de la dépendance `garminconnect` plutôt qu'une séparation
artificielle.

### Interfaces publiques par module


### Flux de données

```
[AUTH] credentials → GNOME Keyring → auth.login() → tokenstore (~/.config)

[GC → WATCH]
  UI sélectionne workouts → sync_workouts.download()
  → garmin_client.download_workout(id) → bytes .FIT
  → sync/workouts.py applique slugify(workout_name) + gestion collisions
  → watch.write_fit(GARMIN/Workouts/{slug}.FIT)
  → store.log_sync(direction="down", ...)
  → store/transfers.py.mark_transferred(file_name, "down", "workout")

[WATCH → GC] (activités)
  watch.list_fit_files("Activity") → fit.classify()
  → sync_activities.upload()
  → garmin_client.upload_activity(path)
  → store.log_sync(direction="up", ...)

[WATCH → GC] (wellness)
  watch.list_fit_files("Monitor"|"Sleep"|"Metrics")
  → sync_wellness.upload()
  → garmin_client.upload_activity(path)  # endpoint générique
```

**Nommage des fichiers workout sur la montre :** les workouts téléchargés
depuis GC sont écrits dans `GARMIN/Workouts/` avec un nom lisible :
`{slug(workout_name)}.FIT`. Le slugify est une responsabilité de
`sync/workouts.py` (Service) — `watch/filesystem.py` (Core) reçoit le
chemin final et écrit, sans logique de nommage.

Règles de slugify :
- Minuscules, suppression des accents (normalisation NFKD)
- Espaces → `_`
- Suppression des caractères non alphanumériques (sauf `_`)
- Longueur max 40 caractères avant l'extension
- **Gestion des collisions :** si `{slug}.FIT` existe déjà, suffixer `_2`,
  `_3`, etc. La vérification d'existence est déléguée à `watch/filesystem.py`
  (via `WatchFilesystem.list_fit_files("Workouts")`).

Note : le nom affiché par la montre vient du champ `wkt_name` à l'intérieur
du fichier FIT, pas du nom du fichier. Le slugify ne concerne que la
lisibilité du système de fichiers USB (FAT32).

**Alternatives écartées :**

- **Monolithe dans un seul fichier** — impossible à maintenir au-delà de 500
  lignes, la complexité des 5 flux métier (auth, download workout, upload
  activité, upload wellness, historique) justifie le découpage.
- **Architecture microservices** — overkill pour un projet mono-utilisateur
  local sans réseau interne ; ajouterait de la sérialisation, de la
  communication inter-processus, et de la complexité opérationnelle sans
  bénéfice.
- **Couplage direct UI ↔ API Garmin** — impossibilité de tester la logique
  métier sans connexion réseau ni montre branchée ; empêche toute
  réutilisation CLI future ; viole la séparation des responsabilités.

**Conséquences :**

- **Structure `src/openrunner55/`** avec un package par module.
- **Testabilité :** chaque module peut être testé avec des mocks pour ses
  dépendances. Les services sont testables sans UI ni montre branchée.
- **Évolutivité :** un mode CLI ou une UI Qt peuvent être ajoutés en
  branchant un nouveau frontend sur la couche Services, sans toucher au
  Core.
- **Risque de sur-découplage :** pour un projet de ~7 jours/homme, 7 packages
  peut sembler excessif. Mitigation : les interfaces restent simples (1-3
  méthodes par module), pas d'injection de dépendances complexe, pas
  d'interfaces abstraites.
- **Point de vigilance :** le découpage de `sync/` en 3 modules
  (workouts, activities, wellness) pourrait être fusionné en un seul module
  `sync.py` si trop fin. À réévaluer après l'implémentation de l'Epic 2 et 3.
- **Le module `ui/`** fait l'objet d'un ADR dédié (ADR-003). Son architecture
  interne (navigation, vues, composants) relève de la responsabilité de l'UX
  Designer.
- **Simplification UI proposée :** une seule vue "montre" unifiée regroupe
  les deux sens de sync (GC → Montre et Montre → GC) avec séparation visuelle
  des sources, plutôt que deux vues séparées. L'UX Designer peut remettre en
  question cette simplification dans son ADR.
