## ADR-003 — Interface GTK 4 + libadwaita (INC-3)

**Contexte :** Le PRD (EF-16, ENF-3) mentionne une interface graphique native,
« GTK privilégié, fallback app web locale si coût trop élevé ». L'incertitude
INC-3 demande de trancher ce choix avant le développement. Le persona utilise
Fedora 44 / GNOME. L'application comporte 2-3 vues principales (authentification,
montre, historique) et une logique métier déjà validée par le spike S-2.

**Décision :** GTK 4 + libadwaita via PyGObject.

Arguments :

| Critère | GTK 4 | App web locale |
|---------|-------|---------------|
| **Intégration GNOME** | Native (thème, dark mode, polices, raccourcis) | Navigateur ou webview externe |
| **Accès système** | DBus natif (keyring, udev, notifications) | Nécessite un bridge Python ↔ JS |
| **Dépendances** | PyGObject, GTK4, libadwaita — dans les dépôts Fedora | Flask/FastAPI + navigateur/webview |
| **Surface de code** | ~200-300 lignes pour 3 vues simples | Serveur HTTP + routes + frontend JS |
| **Complexité opérationnelle** | Zéro (processus unique) | Port, processus serveur, CORS, build frontend |
| **Maintenabilité** | Bibliothèque stable depuis 20+ ans | Stack web = mouvante, plus de couches |
| **Performance** | Native, < 50 Mo RAM | Navigateur = 200+ Mo RAM |

Le coût de GTK n'est pas prohibitif pour ce projet : 3 vues simples (formulaire
login, liste fichiers avec sélection, tableau historique). PyGObject est mature
et documenté.

**Alternatives écartées :**

- **App web locale (Flask/FastAPI + webview/browser)** — ajoute un serveur HTTP
  local, un port à gérer, une couche de bridge entre le Python backend et le
  frontend JS pour l'accès au keyring et à udev. Complexité disproportionnée
  pour 3 vues. Le « coût trop élevé » du fallback PRD ne s'est pas matérialisé.
- **Qt (PySide6)** — mature et multi-plateforme, mais non natif sous GNOME
  (thème différent, pas d'intégration libadwaita). Dépendances plus lourdes.
  Le persona est sur GNOME.
- **Tauri** — framework desktop moderne (Rust + webview), mais pas de bindings
  Python matures pour Tauri v2. Obligerait à écrire une partie en Rust ou à
  utiliser un bridge expérimental.
- **Textual (TUI)** — interface terminal, ne répond pas à l'exigence EF-16
  (interface graphique).

**Conséquences :**

- **Dépendance `PyGObject`** : disponible dans les dépôts Fedora
  (`python3-gobject`, `gtk4`, `libadwaita`). Pas de pip install requis pour
  la partie GTK.
- **Courbe d'apprentissage :** si le développeur ne connaît pas GTK, les
  bindings Python suivent l'API C de GTK (documentation C réutilisable). Les 3
  vues du MVP sont suffisamment simples pour limiter ce risque.
- **Portabilité :** limitée à Linux (Fedora cible). GTK4 fonctionne aussi sur
  d'autres distributions Linux. Pas de support Windows/macOS — hors périmètre.
- **Découplage UI / Core :** ADR-002 garantit que la couche UI peut être
  remplacée sans toucher à la logique métier. Si GTK devenait problématique,
  le fallback app web locale reste possible.
- **Responsabilité UX Designer :** l'organisation interne des vues GTK
  (navigation, layout, composants, séparation visuelle des sources) relève de
  l'UX Designer, qui produira son propre ADR.

**Références :** INC-3 dans le PRD. ADR-002 pour le découplage UI/Core.
